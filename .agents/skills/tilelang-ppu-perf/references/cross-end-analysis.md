# 跨端对比分析（PPU 侧 vs NVIDIA 侧）

定位：本页是本 skill 的**跨端对比层**。单端指标怎么读（SOL、停等分类、端内饱和判断）由对应单端 skill 负责：PPU 侧 `acu-report-skill`，NVIDIA 侧 `ncu-report-skill`。本页只负责"把两份各自已经解读过的报告放在一起对账"。

## 1. 前置条件（不满足就不要开始）

| 条件 | 说明 |
|---|---|
| 两侧**各自完成单端分析** | 不只是两份报告存在，而是每一侧都已产出单端结论：瓶颈假设、停等分解、端内饱和判断。"两份文件都在"不是充分条件 |
| 可比性逐项通过 | 见 Step 0；不通过就是"不可比"，不是"差不多可以比" |
| 交接包完整 | 每份报告的 workload / launch / 版本 / 编译配置 / 产物位置 / 缺失项 / 单位来源，见 [analysis-routing.md](analysis-routing.md) §2 |
| 证据强度已预期 | 两端工具口径不同，跨端结论默认在同级基础上降一档；唯一不降档的是"两侧绝对量直接计数完全吻合"的对账结论（如指令数、交易数、字节数绝对量相等）——绝对量不受工具口径差异影响，可维持"实测" |

## Golden Rule

**对账绝对量 → 指令结构对等 → 停等分解 → 交易效率 → 端内饱和 → 自洽闭环 → 归因输出。**

任何一步闭环不了，就是归因错了，回到上一步重来。跨端分析历史上最常见的错误是**跳步**：从利用率/SOL 排序直接跳到诊断结论（"某端访存管线不行"），中间没有绝对量对账，也没有闭环校验。

## 2. 核心纪律（违反任一条都会导致误判）

1. **SOL% / 利用率% 永不跨端相减**。两端峰值定义与锁频口径都不同。跨端只对账绝对量：duration、LD/ST warp-inst 计数、交易计数、字节数。定性结论（"饱和 vs 半空"）可跨端，定量百分比差不可。
2. **说"饱和"前必须知道容量绝对值**。把实测值换算成占比之前，必须先知道该单元的容量（每周期可发射多少指令、每周期可消化多少 sector）。不知道容量就声称"吞吐贴满"，是跨端分析第一大误判源。
3. **区分背压类与延迟类停等**。背压类（下游管线已满）加 occupancy 无用，只是把队伍排更长；延迟类（数据未回）加 occupancy 有用。具体信号归属与占比读法见 §4.1 指向的单端 skill；归因前必须完成停等分解，否则"加 warp 能不能救"这个问题无法回答。
4. **codegen 产物是第一手证据**。两端报告解读出现分歧时（"这条访存为什么拆成多段""这个转换为什么多两条指令"），去读 DSL 生成源与 host 侧产物，不要从 SASS 反推编译器行为。产物的落地方法见 [codegen-and-save-temps.md](codegen-and-save-temps.md)。
5. **单端指标语义先查对应单端 skill 再解读**。同名指标在不同工具/不同 section 下语义可能完全不同；本页只保留跨端对账必需的概念（§4.1 停等类别）与 SASS 指令语义（§5），指标含义本身见 `acu-report-skill` / `ncu-report-skill`。
6. **SASS 指令语义禁止望文生义**。操作数修饰符（取绝对值、取负）不改变 opcode 名；高层语义（低精度转换、除常数）常被 lowering 成多条指令。语义存疑时按优先级找证据：DSL 生成源 → 编译器文档 → 标注置信度后使用。见 §5。
7. **同名指标按 metric id 对齐，不按显示名对齐**。跨工具、跨 section 的"同名字段"是最常见的假对齐。

## 3. 工作流

> Step 1（证据保全）不在此列：codegen 落地见 [codegen-and-save-temps.md](codegen-and-save-temps.md)，双写归档见 [archive-and-manifest.md](archive-and-manifest.md)。编号沿用历史，避免旧引用失配。

### Step 0：可比性确认（对不齐就停下）

| 项 | 判据 |
|---|---|
| kernel 同一性 | 符号级确认（不是"两个同名文件/同名函数"）；符号名可能带签名哈希后缀 |
| 输入 | 形状、规模、dtype、是否 dynamic shape 一致 |
| 访存模式 | 对齐、padding、布局、是否直通/缓存旁路一致 |
| launch | 实际 grid / block / shared_mem 逐项列出并一致 |
| 版本 | profiler / device 编译器 / host 编译器 / DSL 版本与 commit 均已知且记录 |
| 变量控制 | 若一端是旧版本代码跑的，先向用户确认版本差异是否影响对比，必要时补跑控制变量 |

任一项不过：结论只能是"不可比"。补控制变量或重采（重采前先问用户，别自行占设备）。

### Step 2：工作量对账（绝对量）

两端分别取：总 warp-inst、global / vmem LD 与 ST warp-inst 计数、（若可得）分 opcode 动态计数。

- **LD/ST 计数逐一相同** → 排除"某端访存策略不同"，差距必在每条访存的执行代价或下游消化能力（进 Step 5）。
- **计数不同** → 先解释差异来源（codegen 版本、向量化宽度、循环展开、指令选择）再继续；解释不了说明还有变量没控制住，回 Step 0。
- **同端新旧版本对比**：逐 opcode 动态计数完全相等即证明 codegen 确定性，可排除"版本变量"这一嫌疑。

### Step 3：指令结构对等性验证

把计算链拆成功能环节（载入、规约、scale 计算、逐元素变换、写回……），逐环节比对两端 SASS：

| 环节 | A 端指令 | B 端指令 | 域别/宽度一致？ | 差异来源 |
|---|---|---|---|---|
| | | | | |

同时读 codegen 产物确认每个环节的来源：

- **DSL 源码显式写的** → 两端 codegen 都会忠实还原，属于**源码差距**（改 DSL 源码两端都受益）。
- **后端编译器自己的选择**（指令选择、融合、修饰符、软件 lowering）→ 属于**编译器差距**（改不动，只能绕）。

判定方法：生成源里有对应调用就是前者。**只有后者才算"编译器差距"**——这是本步骤唯一要产出的结论。

### Step 4：停等分解对比（瓶颈的表现形态）

单端各自完成停等分解（方法见对应单端 skill），跨端只比三件事：

1. **占比排序**：各停等原因占比（per issue-active 归一化后）。跨原因只看占比排序，不比总量（分母口径不同）。
2. **类别**：主导停等是背压类还是延迟类——决定"加 occupancy 有没有用"。
3. **对账锚点**：分解各项合计 ≈ cycles per issued instruction。对不上说明指标取错或分母不同，先修口径。

### Step 5：交易效率（每条访存指令的执行代价）

每端按三步算，三步的数字都要写进报告：

1. **实测每条指令交易数** = `实际交易数 ÷ 访存指令数`。
2. **理想每条指令交易数** = `按向量宽度加权的理想交易数 ÷ 访存指令数`。理想值随指令构成变化（宽向量指令每条对应多个 32B sector，标量指令少），**必须按各宽度指令的条数加权**，不要用 naive 的"每条指令理想 = 1~2 交易"——那会对向量指令产生假阳性放大判断。
3. **放大倍数** = 实测每条指令交易数 ÷ 理想每条指令交易数。

放大倍数用来解释字节量：**放大倍数 × 访存指令数 × 理想交易字节 = 该端需消化的实际字节量**（理想交易字节 = 一条理想交易的字节宽度，如 32B sector）。它回答的是"指令数相同，这一端为什么向内存系统多要了那么多字节"。

- 若依赖 DSL：fragment / thread 映射决定地址模式，地址模式决定交易放大。**先看 DSL 源码的元素→线程映射，再解释交易数据**，不要倒过来。

### Step 6：端内饱和判断（谁先饱和）

各端内部判断：哪个单元饱和（对照容量绝对值）、哪些单元有大量余量。跨端比较的是"**同一访存模式下谁先饱和、饱和端对面的余量端处于什么状态**"，不是"两端利用率谁高"。

### Step 7：自洽闭环校验（两道，缺一道就不能下结论）

| 闭环 | 校验 | 不成立说明 |
|---|---|---|
| 停等闭环 | stall 分解各项合计 ≈ cycles per issued instruction | 指标取错或分母不同 |
| 端到端闭环 | 用独立因素（带宽、交易量、指令数差异）算出的 duration 比值预测，与**实测** duration 比值对照 | 吻合（误差 <5%）→ 该因素组合解释了差距；不吻合 → 还有未找到的因素，回 Step 2 |

**端到端闭环不能写成"吞吐比 ≈ 时长反比"**：两者互为倒数，是恒等式，永远成立，因此不携带任何信息，更不能用来证明"某因素解释了 100% 的差距"。闭环必须由指令数 / 交易数 / 字节数 / 容量这些**独立于时长**的观测量算出预测值，再与实测时长比对照。

### Step 8：归因输出

- 按贡献度排序各因素（例：某端管线饱和 × 交易放大 → 主因；后端指令数差 → 次因）。
- 每条附**支撑指标对**（A 端值 / B 端值）+ 证据强度 + 成立边界。
- 优化建议必须区分两类，不能混着写：
  - **改 DSL kernel 源码**（两端受益，可执行）
  - **某端编译器/硬件限制**（改不动，只能记录为"已解释的差距"）
- 修正早先结论时在报告头部保留修正链，不静默改写。

## 4. 跨端对账的概念边界与允许/禁止的对比方式

### 4.1 停等类别（跨端只需这一层区分）

跨端只需要一个停等概念：**背压类**（下游管线已满，warp 在排队）vs **延迟类**（依赖数据未回，warp 在等空窗）。它决定"加 occupancy 有没有用"这个问题能不能回答，所以跨端必须区分。**哪些信号属于哪一类、各类占比怎么读、怎么优化，一律见对应单端 skill**（PPU 侧 `acu-report-skill`，NVIDIA 侧 `ncu-report-skill`）——本页不列映射表、不给优化方向、不解读单端指标。

### 4.2 允许 / 禁止的跨端对比方式

| 对比方式 | 允许？ | 说明 |
|---|---|---|
| duration / cycles 比 | 允许（绝对量） | 锁频差异必须在报告里说明口径 |
| 指令计数、交易计数、字节数比 | 允许（绝对量） | 逐项列出，不要只给总量 |
| "A 端某单元饱和 vs B 端同功能单元半空" | 允许（定性） | 两侧的容量绝对值都要写出来 |
| SOL% / 利用率% 跨端相减 | **禁止** | 口径不同，差值没有意义 |
| 跨端比 IPC 数值 | **禁止** | 发射容量不同；只能各自端内归一成"发射槽利用率%"再比 |
| 按显示名把两侧指标配对 | **禁止** | 按 metric id 对齐 |

## 5. SASS 语义速查（判读原则：望文生义是误判第一来源）

### 5.1 NVIDIA：操作数修饰符（最易误读）

修饰符写在操作数位置，不改变 opcode 名，导致"看 opcode 猜功能"必然出错：

| 修饰符 | 含义 | 误判形态 |
|---|---|---|
| `\|Rx\|` | 取绝对值 | 形如 `HFMA2 R2, -RZ, RZ, \|Rx\|` 的指令实际是 **abs**（单目运算被 FMA 形式借用来实现），不是"乘法融合进半精度域" |
| `-Rx` | 取负 | 形如 `HADD2 R4, -R2, RZ` 是取负，不是减法优化 |

### 5.2 NVIDIA：常见双元素 / packing 指令

| 指令族 | 语义 |
|---|---|
| `HFMA2.*_V2` | 半精度 x2 融合乘加（2 元素/条）；也常被借来实现 abs/negate 等单目运算 |
| `VHMNMX.*_V2` | 半精度 x2 min/max 融合，常见于 absmax 规约链 |
| `HADD2.*_V2` | 半精度 x2 加法 |
| `F2FP.SATFINITE.*.PACK_AB_MERGE_C` | f32×2 → fp8×2 打包转换（2 元素/条） |
| `FMUL` / `FFMA` / `FMNMX` | f32 标量域的乘 / 融合乘加 / min-max |
| `LDG.E.128` / `STG.E.128` | 128-bit 向量 global 读 / 写 |
| `STG.E.U8` | 单字节写（窄写，注意交易效率） |
| `PRMT` | 字节重排，常用于低位→高位精度的位搬移 |
| `IMAD` / `IMAD.MOV` | 整数乘加；`IMAD.MOV ..., RZ, RZ, RZ` 就是寄存器清零（move 的伪装） |
| `LOP3.LUT` | 3 输入按位逻辑（查表实现任意 and/or/xor） |

### 5.3 NVIDIA：常见软件 lowering（不是硬件指令）

| 高层操作 | 实际生成的指令序列 |
|---|---|
| bf16 → f32（每 2 元素） | `PRMT`（抽高 16 位）+ 左移 + 整数乘等——**整数位操作，不是一条转换指令** |
| 除以常数 | 乘以倒数近似 + `FFMA` 修正 |
| warp 内规约 | shuffle / 共享内存指令序列，非单条 |

**含义**：低精度→f32 的转换在 NV 侧不一定免费。若对端有专用转换指令（1 条 / 2 元素），转换环节反而可能对端更省——这类差异要归到"后端指令选择"，不是"源码写法"。

### 5.4 PPU（vmem）指令宽度与交易理想值

| 指令形态 | 每元素字节 | warp（32 lane）每条理想交易数（32B sector） |
|---|---|---|
| 标量 b32 读 / b8 写 | 4B / 1B | 2 / 1 |
| b32x4 写 | 16B | 8（warp 内地址连续时） |
| b32x4 读 | 16B | 8 |

**交易/指令比的理想值必须按指令构成加权**（例如 ld 由 b32x4 与 b32 混合时按各自条数加权），否则向量指令会被误判成"严重放大"。

### 5.5 PPU 常见计算指令

| 指令 | 语义 |
|---|---|
| `v.abs.*x2` / `v.max.*x2` | 半精度 x2 SIMD 单目 / 比较（与 NV 的 FMA+修饰符、VHMNMX 功能对等） |
| `v.cnvt.f32.bf16` | bf16→f32（每条 2 元素）；注意头文件的软件 fallback 会展开成多条整数指令 |
| `v.pcnvt.*x2.f32x2.*` | f32×2 → fp8×2 打包转换 |
| `v.mul.f32` / `v.fma.f32.*` | f32 标量域乘 / 融合乘加 |
| `v.and/b32`、`v.shrl/sll.b32` | 位操作（指数域提取常用） |
| `v.madl.i32` / `v.madw.i64.i32` | 整数乘加（地址计算主力） |
| `s.*` 前缀 | 标量域 / 系统指令（控制流、共享寄存器） |

### 5.6 跨端同构性比对表模板

| 功能环节 | NV SASS | PPU SASS | 域别一致？ | 宽度一致？ | 差异来源 |
|---|---|---|---|---|---|
| （例）逐元素乘 scale | f32 `FMUL` | `v.mul.f32` | 一致 | 一致 | 无 |
| （例）abs | `HFMA2` + `\|R\|` 修饰符 | 专用 `v.abs.*x2` | 一致 | 一致 | 后端指令选择 |
| （例）bf16→f32 | 3 条整数位操作 | 1 条转换指令 | 一致 | NV 多 2 条 | 后端指令选择 |

**差异来源只有两类**：DSL 源码写法（两端都忠实还原 → 源码差距）或后端编译器选择（指令选择/融合/修饰符 → 编译器差距）。判定方法：读生成源，源里有对应调用就是前者。

## 6. 证据强度分级与降级声明

| 级别 | 定义 | 示例 |
|---|---|---|
| **实测** | 报告中的直接计数 / 比率 | duration、LD/ST warp-inst、交易计数、停等分解占比 |
| **推断** | 由实测值反推，或单边实测 + 另一侧容量/余量反推 | 管线吞吐上限（实测交易量 ÷ 实测周期）、由静态 SASS 推的动态占比、单侧停等 + 另一侧余量推出的结论 |
| **假设** | 未经指标验证的机制解释 | "编译器应该会……" |

**必须降级的情形**（降级要写进报告，不能悄悄给一个看起来很确定的结论）：

- 某侧采集 set 不全、关键 section / 停等指标缺失 → 该维度结论封顶"推断"。
- per-PC / 逐指令停等为空 → 禁止据此刻画到具体指令，只能做 kernel 级描述。
- 某侧只有 bench 数字没有报告 → 只能给"现象"，不能给"机制"。
- 跨端结论默认在同级基础上再降一档（工具口径不同）。**这不是例外，而是判据不同**：两侧绝对量直接计数完全吻合的对账结论（指令数 / 交易数 / 字节数绝对量相等）可维持"实测"——降档的理由是工具口径差异，而绝对量对账不依赖峰值与锁频口径，这条理由在这类结论上不成立。
- 单位或导出来源不明 → 该数值只能当量级参考。

## 7. 结论落地格式

结论模板（支撑 / 对照 / 强度 / 边界）以 [analysis-routing.md](analysis-routing.md) §7 为唯一出处，此处不重复定义。跨端只额外加两条约束：

- "对照"行必须是**另一端的同 metric id 数值**，并写出该端的列名、单位与聚合层（sum / avg）。
- 每条结论标注它在归因里的角色（主因 / 次因），并按贡献度排序。

追不到"文件 + 列名 + 值"的结论，一律降级或删除。

## 8. 常见陷阱速查

| 陷阱 | 后果 | 规避 |
|---|---|---|
| 从利用率/SOL 排序直接下诊断 | 归因建立在跨端口径差上 | 先做 Step 2 绝对量对账 |
| 不知道容量就说"贴满/饱和" | 把远未饱和的发射占用说成瓶颈 | 先查容量绝对值，再换算占比 |
| 把背压类停等当延迟类 | 建议"加 occupancy"，改了没用 | 先做停等分解与分类 |
| 用 naive 理想交易数评向量指令 | 假阳性"交易放大" | 按指令宽度加权理想值 |
